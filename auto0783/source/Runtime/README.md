# Trusted Harbor infrastructure

This runtime supports native Harbor 0.23.0 on an ARM64 Docker host with separate network-none Agent and Verifier roles. Install the pinned Harbor requirement, materialize the Task dependencies, expose Docker on the trusted launcher's PATH, and add this Runtime directory to the launcher's import path.

Use `hybrid_harbor_environment:HybridDockerEnvironment` for ordinary roles and `oracle_exec_environment:OracleExecDockerEnvironment` only for an explicitly authorized native Oracle. The Oracle extension preserves the tested executable author mount repair. It does not apply to candidate roles.

The trusted launcher must pass an absolute `runtime_root` for its own evidence and a `numerical_status` path for an already provisioned numerical controller. These locations are host-only; they are never candidate-selected or mounted into a candidate role. Each role has its own unique Docker queue and evidence directory. The existing data-only relay binds the fixed public tensor manifest, assigns Dev or formal profile by physical role, and checks live controller PIDs and result lineage. Neither a configuration file nor this README is proof of a live numerical backend.

For model authoring, the trusted launcher registers an in-memory callable with `hybrid_relay.register_credential_provider(callback)` before creating native Harbor Trials. The callback receives the physical role. Keep the callable outside TrialConfig: only `runtime_root`, `numerical_status` and other non-secret strings belong in serializable environment kwargs. A direct Python environment constructor also accepts a `credential_provider` callback, but it must not be serialized as configuration. For the assigned GPT campaign this must delegate exclusively to the task's approved keychain reader. For Seed it must use the user's existing official Ark CLI profile. Implementations and credentials stay outside the delivered package; no new provider account is created. The relay calls the callback lazily and only for a permitted model operation. NOP, Oracle, isolated artifact transfer and numerical validation do not need a model credential. A Verifier can never load one. No credential is written into candidate ENV, Task or the descriptor. Fixed lane models, high effort, endpoints and disabled response storage remain enforced by the relay. Optional `model_proxy` is an explicitly trusted loopback URL; ambient HTTP proxy environment is ignored.

Selected methods, all mathematical evaluators, hidden/public inputs and bounded artifact transfer retain their source identities. The broker and Oracle mount repair are exact copies of the previously used infrastructure. ## Native validation entry points

Restore the complete Task with dependencies/task/materialize_task.py and verify its 39-file identity. Provision the declared trusted numerical inputs, pinned dependencies and public weight service, or attach the already live approved controller. Keep runtime evidence outside both Task and Runtime. Set PYTHONDONTWRITEBYTECODE=1 when launching the entry points.

```sh
python Runtime/run_isolation.py --task materialized-Task --runtime-state validation-state --numerical-status trusted-controller-status.json
python Runtime/run_native_validation.py --mode nop --task materialized-Task --runtime-state validation-state --numerical-status trusted-controller-status.json
```

The isolation entry is an actual three-role native Docker probe with physical queue separation, network-none/UID/credential/hidden/Reference negatives and bounded artifact roundtrips. It submits no numerical or model request. The numerical validation entry defaults to describe-only. After matching isolation and actual resource availability, add --execute exactly once for each required validation stage. Run nop, oracle, then selected with --lane gpt and --lane seed. The repaired Oracle uses the exclusive executable author mount; selected validation copies only each native author's frozen pair into its own ordinary role. A changed Task, runtime source, dependency script/descriptor or selected pair invalidates the source-bound isolation proof. All failure attempts retain their real native trial ID, original result and evidence. Do not repeat an in-flight request or start another worker to bypass a shared lock.

A native successful result is explicitly PASS_NATIVE_FULL_GPU_CPU_AUDIT_PENDING. This is not an independent CPU, stability, final ZIP or QA pass.
